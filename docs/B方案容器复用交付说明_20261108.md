# B方案容器复用交付说明（0.5.0）

2026年11月8日，按用户反馈，将新视频任务从“每个分片单独启动容器”的A模式改为B模式：每个参与节点在任务内保留一个执行容器，模型只加载一次，连续处理多个视频分片；任务结束后统一回收。代码、构建、测试和正式部署均在服务器 `/root/projects/changan-orchestrator` 完成，本地仅同步资料和交付证据。

## 已交付的行为

- 新增任务内节点执行会话，与分片尝试分开持久化。首次分配时按需启动容器，之后复用相同Pod UID和模型，暂时无片可处理时等待。
- 分片成功以结果来源、模型和输入摘要、采样结果及持久化产物校验为准，不再等待容器退出；一个分片完成即可继续分配下一片。
- 任务完成、失败、取消或超期后回收其会话。已完成分片保留；普通分片失败可复用健康会话重试，Pod/节点异常或超时才更换会话。
- 节点动态加入后可参与剩余分片调度；节点失联时撤销旧会话执行权并重排未完成分片，旧结果不能覆盖有效尝试。失联节点资源保持隔离，待终止或恢复后的清理证据确认后释放。
- API与内部网关重启后恢复持久化会话和当前分片，不重新启动已运行的健康容器。结果回执可幂等重传。
- 内存和执行槽按会话预留，分片完成时仅释放会话内部的分片占用。外部资源池预留接口同步改为会话范围，实际资源池联调仍待开展。
- “容器与镜像”页新增节点会话表，显示Pod身份、已处理分片数、模型加载次数/耗时和回收状态；分片表关联所属会话。导出包含脱敏会话证据，历史A模式任务明确按原方式展示。

## 使用与源码位置

通过原8310端口页面提交新任务即可使用B，不需要逐节点启动worker。查看“任务详情 → 容器与镜像”，同一会话多个分片应拥有相同Pod UID，模型加载次数应为1。

[任务会话使用说明](K3s任务会话使用说明_20261108.md)包含日常运行、节点加入/退出、资源预留、异常恢复、验证与复现方式。[验证记录](B方案验证记录_20261108.md)列出各场景结果。

源码主要变更为 `app/session_execution.py`、`app/engine.py`、`app/container_execution.py`、`app/db.py`、`app/kube.py`、`workers/container_entry.py` 以及前端会话展示。旧分片入口保留在 `workers/attempt_entry.py`，用于历史任务兼容和隔离A/B实验；新建业务任务默认使用B。

## 部署与限制

正式管理API仍绑定 `127.0.0.1:8310`，内部容器网关为当前集群网桥地址8311，Redis维持运行；隔离验证实例8410/8411已关闭。备份位于 `data/backups/20261108-task-sessions`，含升级前数据库、环境配置和前端。备份凭据不入库。如需回退，先确保所有任务终止且会话资源清理完成，再使用对应版本和备份，避免丢弃新版本产生的业务数据。

当前验证仍是单台开发服务器中的4个K3s逻辑节点、amd64镜像、CPU ONNX推理。THOR硬件、ARM64镜像、GPU后端、真实车载网络及正式资源池服务尚未完成适配/联调。本轮没有宣称这些内容已完成。

每任务每节点一个会话，同一会话串行处理分片；健康会话在任务内保留，暂未实现跨任务模型共享、空闲会话抢占或外部资源池动态续约。K3s故障期间已失联设备可能短时仍运行，但旧会话结果被隔离；不以强删API对象冒充真实设备已停止。
