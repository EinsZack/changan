# GPU 容器执行部署与使用说明（0.6.0）

## 已接入的执行方式

任务提交时固定 CPU 或 CUDA 后端、模型摘要和各 CPU 架构对应的镜像摘要。业务调度选择符合资源条件的节点，K3s 创建任务内执行会话；一个任务在一个节点上只加载一次模型，连续处理多个视频分片，任务结束后清理。

CUDA 会话申请 `nvidia.com/gpu: 1`，使用 `RuntimeClass=nvidia`。容器必须恰好看到一个 GPU，CUDA 驱动返回的 UUID 必须与分配设备匹配；ONNX Runtime 必须加载 CUDAExecutionProvider，并在预热的分析记录中出现实际 CUDA 计算事件。验证不通过时任务失败或重试，禁止整模型静默回退 CPU。ORT 允许形状等辅助算子放在 CPU，回传各执行提供程序的事件数。当前视频解码、图像前后处理仍由 CPU 完成。

本次服务器使用一个专用 GPU 逻辑节点 `gpu-1`，映射一张共享 RTX 5090；另外四个逻辑节点保持 CPU 执行。所有节点共用同一台开发服务器，既不是五台独立设备，也不是四块 THOR。其他服务器进程仍可能使用这张卡，设备显存/利用率包含它们的占用。

## 网页与 API

1. “新建分析任务”选择“推理后端”。正式部署默认 CUDA；可显式选择 CPU 并指定 lab-1～lab-4 做原有流程验证。
2. CUDA 可设置最低空闲显存，默认 2048 MiB。该数值也配置 ORT GPU 内存池上限，但不是整个进程显存的硬配额；CUDA 上下文、cuDNN 工作区等可能额外占用。任务启动后显存仍受共享服务器其他进程影响。
3. “候选节点筛选”选择同一后端，可查看架构、资源、占用、显存不足和数据过期的排除原因。GPU 状态缺失时不自动换 CPU。
4. “执行节点”查看 GPU UUID、设备空闲显存、利用率及 CPU/CUDA 各自的实测处理吞吐。
5. “任务详情 → 容器与镜像”查看持续复用的 Pod、模型加载次数、实际执行提供程序、GPU UUID、预热和 CUDA 算子事件。分片表中的“模型计算”只统计 Session.run；“传输与吞吐”的处理耗时还包含视频解码、前后处理，父任务耗时进一步包含调度、传输和首次启动等。

```json
{
  "name": "CUDA 视频任务",
  "source": "demo",
  "inference_backend": "cuda",
  "min_gpu_memory_mb": 2048,
  "segment_seconds": 1,
  "sample_fps": 15,
  "node_ids": ["gpu-1"]
}
```

提交接口 `POST /api/tasks`；`GET /api/execution-profiles` 返回已配置镜像的后端及架构，不等同于当前有空闲节点。`POST /api/scheduling/candidates` 按实时资源进一步判断。旧任务、旧决策不改写；旧任务重跑和已有策略缺少后端字段时按原有 CPU 语义处理。

## 服务器构建与运行

所有命令在 `/root/projects/changan-orchestrator`、专用 Python 环境执行。Docker 仅用于构建镜像及外层开发节点，业务容器由 K3s/containerd 运行。

```bash
source /root/miniforge3/etc/profile.d/conda.sh
conda activate changan-orchestrator
# 下载到项目目录，校验值由仓库锁文件固定。需要时先在同一 shell 执行 magic on。
python -m pip download --only-binary=:all: --require-hashes \
  -r deploy/requirements-video-cuda.lock.txt -d tmp/gpu-build/wheels
python scripts/build_gpu_image.py
python scripts/build_video_image.py
```

构建命令只输出镜像摘要，不自动切换运行环境。CPU 摘要在 `tmp/cpu-image.txt`，CUDA 摘要在 `tmp/gpu-build/cuda-image.txt`。只有明确使用 `build_video_image.py --configure` 才会改 CPU 配置。

将 `.env` 对应字段设置为验证后的摘要：`CHANGAN_VIDEO_IMAGE`、`CHANGAN_VIDEO_CUDA_IMAGE`、`CHANGAN_DEFAULT_INFERENCE_BACKEND=cuda`。示例见 `configs/gpu.env.example`。运行前检查在途任务并备份 SQLite、环境配置和前端产物，再用 `scripts/manage.py restart api container-gateway` 切换。GPU 设备级遥测服务由 `CHANGAN_GPU_TELEMETRY=server` 启用，正常间隔 5 秒；超过 20 秒的遥测不支持新 CUDA 分配。

开发服务器嵌套 GPU 节点使用 `scripts/build_lab_gpu_node.py` 和 `scripts/setup_gpu_node.py --gpu-uuid <实际UUID>`。构建脚本校验官方 Toolkit/发行版软件包，保留驱动库版本文件和符号链接；驱动必须与当前服务器一致。该镜像仅用于当前嵌套开发环境，不能复制到 THOR。重建节点须确认没有业务任务，保留命名卷，尤其 `/etc/rancher/node` 的节点身份。受限网络需将已校验的 `data/k3s/pause.tar` 导入新增节点 containerd。

`deploy/nvidia-device-plugin.yaml` 是当前服务器单卡专用清单，按节点名和 GPU UUID 限定设备。不能把这一 UUID 复制给其他逻辑节点，也不能把该清单直接作为四板通用配置。重复 GPU UUID 注册会阻止 CUDA 调度。

## 调度与资源池接口

- 每个 GPU 节点当前支持一个可见 GPU、一个会话占用该 GPU；暂未实现同卡多会话共享、MIG、MPS、显存细分调度。
- GPU 空闲数同时考虑集群全部命名空间的 Pod GPU 请求以及本系统尚未回收的会话预留。Kubernetes 是实际设备分配的最终执行方。
- 会话复用可使用已持有的 GPU 和内存，不把自身占用再算作不可用；其他任务等待资源释放。取消、异常和重试按实际容器清理结果释放资源。
- CPU/CUDA 吞吐分别记录，并匹配模型、节点身份和镜像；新镜像没有实测时使用明确标识的初始估计。下载带宽反馈沿用 0.5.1。
- 资源池预留参数新增 `inference_backend`、`gpu_count`、`gpu_memory_mb`，仍以任务内会话 ID 为幂等键，已有 `memory_mb`、`slots`、`scope=task_session` 保留。
- 节点侧遥测注解 `changan.io/gpu-telemetry` 为 JSON：`uuid`、`name`、`memory_total_mb`、`memory_free_mb`、`memory_used_mb`、`utilization_percent`、`observed_at`（Unix 秒）。必须对应 `changan.io/gpu-uuid` 标签。监控失效时保持未知，不用虚拟数值顶替。
- 正式资源池仍待与顾强强联调。权限方面，编排器新增读取集群 Pod 的权限以核对 GPU 占用，业务写权限仍限定在 changan 命名空间；遥测脚本使用开发集群管理员凭据，板端正式权限需单独划分。

## THOR 接入准备

已准备按架构选择不可变镜像的协议、板端只读检查脚本和 ARM64 镜像模板。未声明 ARM64 镜像或 THOR 已验证。

1. 到货后在实际板卡运行 `python3 scripts/board_gpu_preflight.py`，记录系统、架构、内存、CUDA 驱动及 NVIDIA 容器运行时情况。先确认具体产品和官方系统属于 Jetson/Linux 还是 DRIVE 平台，不预先指定 JetPack/DriveOS 版本。
2. 使用该系统支持的驱动、Container Toolkit 与 K3s/containerd 组合。物理板卡按官方部署方式安装设备插件；无需嵌套 Docker 开发节点或服务器驱动拷贝。
3. 选择匹配实际 BSP、Python、CUDA/cuDNN 的官方 ARM64 基础镜像，基于 `deploy/Dockerfile.video-arm64.template` 生成板卡专属依赖锁和镜像。模型摘要保持一致，先预拉取/导入已验证镜像，避免首次大镜像下载消耗业务任务时限，再验证非 root、只读根文件系统、一个可见 GPU 及真实 CUDA 算子，再配置 `CHANGAN_VIDEO_CUDA_IMAGE_ARM64=<已验证摘要>`。
4. 板端资源采集提供同一遥测协议。若使用统一内存，必须注明设备/系统内存的统计语义，由板端实测制定准入预算，不能照搬 RTX 5090 的独立显存数值。
5. 先接一板验证视频上传、分片下载、GPU 会话复用、取消回收和断连恢复；再接四板并发。每板独立业务 ID/节点 UID/GPU UUID，核查目标节点与实际 Pod 落点。
6. TensorRT/FP16、硬件编解码、零拷贝和性能调优留待板卡环境确认后评估。本轮实现 ONNX CUDA，不将它们写成已完成能力。

## 复现测试

```bash
TMPDIR=/dev/shm python -m pytest -q
# 在隔离实例 8410/8411、data/k3s-validation 下运行，禁止指向正式数据库。
python scripts/integration_gpu.py
cd web
npx playwright test -c playwright.gpu.config.js
```

集成用例包含 GPU 连续 24 分片、CPU 回归、无 GPU 时禁止回退、等待/取消/释放、控制面重启和 GPU Pod 中断恢复。报告保存实际镜像摘要、任务 ID 和环境；执行性能需在同条件下单独比较，不能把开发服务器数据算作真实车端验收。
