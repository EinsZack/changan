# 原四节点通用 CPU/GPU 运行环境

日期：2026年11月8日。业务版本保持0.5.1，运行环境单独标记runtime1。以下操作在服务器`/root/projects/changan-orchestrator`和项目专用Conda环境中执行。

## 此轮解决的层次

原lab-1～4是同一物理服务器上的k3d节点容器，业务Pod由节点内部的K3s/containerd运行。仅替换业务Docker镜像不能解决设备访问：此前节点缺少NVIDIA运行时，普通业务Pod缺少GPU设备和驱动库注入；原业务镜像也只有CPU推理依赖。

现在四个原节点使用相同的通用节点镜像，保留CPU和内存资源，并登记GPU；统一业务镜像同时包含ONNX Runtime的CPU/CUDA提供程序、CUDA12.8和cuDNN9依赖。GPU Pod使用nvidia RuntimeClass取得设备和驱动后，同一Python进程可以创建CPU及CUDA模型会话，不需要换节点或重建容器。

本次没有修改app/、workers/、web/的0.5.1业务逻辑。当前网页提交的视频任务仍按原程序显式使用CPU，默认会话Pod也尚未请求GPU。环境支持GPU与当前业务已自动使用GPU是两项不同状态。接入后续模型代码时，需要同时在会话Pod声明GPU设备，并在模型层选择提供程序/设备；无需恢复已撤回的独立gpu-1或任务级CPU/CUDA分流架构。B模式的任务内容器复用机制保持。

## 四个lab共享物理GPU

用户已明确允许服务器仿真中多个lab重复使用同一物理GPU。因此映射校验不要求跨lab唯一，不实施跨lab的GPU去重或物理独占准入。

实际映射位于服务器`data/runtime/unified/gpu-map.json`，支持一个GPU UUID、逗号分隔的多个UUID或`all`。多卡和all的配置解析已单测；本轮实际Pod验证使用单卡共享配置。当前四个lab均映射同一个RTX 5090（当前宿主机索引6）。UUID比索引更适合持久配置；宿主索引6进入仅暴露该卡的业务容器后通常为设备0。模型的device_id按照容器内可见设备序号选择，不能直接照搬宿主索引。

Kubernetes每个lab报告一份GPU资源，四个lab合计的逻辑数4实际对应同一张物理卡。显存和计算能力共享；不能将逻辑资源合计作为四张卡的真实容量或独立性能。本次不改变宿主驱动，也不停止服务器其他用户的GPU进程。容器只能使用部署时已暴露的设备；Python代码选择设备不能绕过设备注入。

## 构建

```bash
cd /root/projects/changan-orchestrator
source /root/miniforge3/etc/profile.d/conda.sh
conda activate changan-orchestrator
mkdir -p tmp/gpu-build/wheels
python -m pip download --only-binary=:all: --require-hashes \
  -r deploy/requirements-unified-runtime.lock.txt -d tmp/gpu-build/wheels
python scripts/build_unified_runtime.py
```

构建输出的不可变镜像引用记录于`data/runtime/unified/images.json`；镜像推送到本项目内部仓库。镜像层/软件包和模型均记录摘要。节点镜像从当前服务器复制匹配590.48.01的驱动用户态库，构建脚本会拒绝未验证的其他驱动版本。软件包、Python轮子及基础镜像均固定版本/摘要。下载不畅时按已有授权在同一会话启用服务器提供的代理，勿把代理变量或凭据写入文档。

这套构建仅验证Linux amd64服务器；THOR是后续ARM64/BSP适配对象，不能直接部署本镜像后宣称已适配。

## 原节点迁移及恢复

当前集群已完成迁移，不要再次运行`cluster.py create`。正常启动仍使用`cluster.py start`和`manage.py start`，现有节点容器采用自动重启策略。新建的标准k3d集群需要执行环境升级。

迁移前等待业务任务进入终态，再停止API和内部网关。脚本会检查在途任务、API进程和节点上的非系统Pod，保留原节点名称、Node UID、持久卷、资源限制和k3d初始化脚本。IP由Docker分配并重新读取，不承诺固定IP。

```bash
python scripts/manage.py stop api container-gateway
python scripts/upgrade_lab_nodes.py upgrade \
  --mapping data/runtime/unified/gpu-map.json \
  --backup data/backups/20261108-unified-nodes --node lab-1
# lab-2、lab-3、lab-4分别顺序执行；检查每个节点成功后再继续。
python scripts/manage.py start
```

本轮备份位于`data/backups/20261108-unified-nodes`。每节点保留原容器快照与元数据，数据库和正式.env另有备份。备份和node-identity目录包含凭据，只留服务器忽略目录，切勿入库或推送node-backup镜像。

需要恢复某个原节点时，在同样无在途任务、API停止的条件下，将上述action改为`restore`。脚本撤下该节点设备插件并恢复其原镜像/卷/身份，支持已验证的迁移失败自动恢复。如果要修改已升级节点的映射，先restore该节点，再修改映射并upgrade；脚本拒绝对已升级容器直接叠加挂载。不要恢复旧数据库来回退节点。

如果需要恢复旧业务镜像，仅将.env中的CHANGAN_VIDEO_IMAGE恢复为备份中的原值并重启API/网关；不要覆盖当前数据库或整份配置。

## 普通业务Pod与模型调用

统一业务镜像默认入口仍是0.5.1任务执行器。诊断Pod覆盖入口为`python /opt/diagnostics/cpu_gpu_probe.py`，属于真实模型诊断，不是正式视频任务。

同一镜像可运行普通CPU Pod，也可运行同时拥有CPU/内存/GPU的Pod。需要GPU时关键配置为：

```yaml
spec:
  runtimeClassName: nvidia
  containers:
    - name: compute
      image: <images.json中的business.cluster_ref>
      resources:
        requests:
          cpu: "1"
          memory: 2Gi
          nvidia.com/gpu: 1
        limits:
          cpu: "2"
          memory: 2Gi
          nvidia.com/gpu: 1
```

CPU程序可以继续使用这个GPU可见容器的CPU。上面不是GPU专用业务节点；runtimeClass指定设备/驱动注入方式，GPU申请指定容器获得的设备数量。部署多个可见GPU时，资源数量应与需要暴露的数量一致。

模型层最小调用方式：

```python
import onnxruntime as ort
ort.preload_dlls()
cpu = ort.InferenceSession(model_path, providers=["CPUExecutionProvider"])
gpu = ort.InferenceSession(model_path, providers=[
    ("CUDAExecutionProvider", {"device_id": 0}),
    "CPUExecutionProvider",
])
# 按需要调用cpu.run(...)或gpu.run(...)，并在任务内缓存模型会话。
```

CPU/GPU会话使用同一容器资源。实际模型可缓存其中一种或多种会话，选择策略属于模型层；无需逐分片启动容器。验证脚本额外核对CUDA计算事件，避免仅凭可枚举CUDA提供程序就宣称GPU已执行。

## 复验

```bash
python scripts/verify_unified_nodes.py
python scripts/verify_unified_nodes.py --concurrent \
  --report docs/unified-nodes-20261108/shared-gpu-concurrent.json
python -m pytest -q
```

第一项验证同镜像CPU Pod和每个lab的同进程CPU→CUDA→CPU。第二项在四个lab同时启动GPU可见Pod，要求容器执行区间实际重叠；共享同一UUID。脚本记录Pod UID、镜像ID、容器ID、实际计算提供程序、输出误差及清理结果，并删除临时Pod/命名空间。运行复验前应保证lab有足够空闲资源；同名验证命名空间不能并行运行两份脚本。

官方依据：K3s Advanced/NVIDIA runtime、NVIDIA k8s-device-plugin及ONNX Runtime CUDA Execution Provider。部署结论以本目录当前实测报告为准，不以旧0.6.0证据替代。

## 迁移中修复的问题

1. 原Docker网络由自动地址池建立，不接受通过IPAMConfig强制指定旧IP。迁移脚本改为保留DNS名称/别名并允许Docker分配地址，随后读取实际Kubernetes InternalIP；本轮实际地址仍与原来一致，但不将其作为后续保证。
2. 自建节点镜像直接启动k3s时漏掉了k3d注入的cgroup v2、挂载传播和DNS初始化脚本，导致首个试点节点kubelet启动失败。自动恢复原镜像后，迁移改为持久保存并挂载原k3d启动脚本，继续使用原Entrypoint；最终各节点的普通Pod已成功启动并运行模型。
3. Ready条件时间戳可能在重启后一段时间内不变化。健康确认同时检查原Node UID、Ready条件和新Node Lease，再以设备插件与真实业务Pod验证运行时，而非只等待旧Ready时间戳变化。

这些失败发生在API停止、无在途任务的维护窗口，未恢复或覆盖业务数据库。原lab-2快照恢复已实际成功验证。
