# 通用CPU/GPU节点环境交付说明

日期：2026年11月8日。基线提交f937605，业务版本0.5.1，环境版本runtime1。开发、镜像构建和验证均在服务器`/root/projects/changan-orchestrator`完成。

## 结论

原lab-1～4已全部升级为通用CPU/GPU节点，保留原节点名称、Node UID、数据卷和CPU/内存限制。没有另建GPU专用业务节点。按用户明确要求，四个lab现在允许并实际共享同一张物理RTX 5090；跨lab的GPU唯一性不作为硬约束。

统一业务镜像包含CPU与CUDA推理依赖。四个节点上的普通非特权Pod均已在同一Python进程完成CPU→CUDA→CPU的YOLOX Tiny真实推理，CUDA分析记录每次203个计算事件。CPU/GPU原始输出最大绝对误差约1.18e-5，在rtol=0.002、atol=0.0002的验证容差内。CPU再调用使用原缓存会话，无需重建容器。

四Pod同时运行的实测也通过：四个容器均看到同一个GPU UUID，执行区间共同重叠于2026-11-08 08:09:56—08:10:08 UTC（北京时间16:09:56—16:10:08）。这证明当前仿真允许跨lab共享物理GPU，不将逻辑登记的4份资源计作4张物理卡。临时Pod和命名空间均已清理。

## 改动

- 节点镜像：K3s1.35.5、NVIDIA Container Toolkit1.18.2、匹配服务器590.48.01驱动的用户态库。默认runc继续运行普通CPU Pod，nvidia RuntimeClass用于GPU设备/驱动注入。
- 业务镜像：Python3.11、ONNX Runtime GPU1.23.2、CUDA12.8、cuDNN9.10及CPU执行依赖；24个轮子记录SHA256，CPU和CUDA共用同一镜像。
- 可配置GPU映射：允许跨lab重复GPU；支持单卡、多卡和all的配置语义。实际Pod验证使用四lab共享单卡；多卡解析有单测。
- 迁移/恢复脚本：先检查无在途任务和API停止，保存原容器快照及节点身份，保留卷和k3d启动脚本，自动处理失败恢复。实际验证过lab-2恢复，迁移期间发现并修复的网络与cgroup问题见使用说明。
- 验证脚本：同镜像CPU-only、每节点同进程CPU/CUDA切换、四节点同时共享GPU，并保存真实计算与容器身份记录。

## 当前边界

本轮保持app/、workers/、web/与f937605完全一致，没有重新引入已撤回的0.6.0任务级CPU/CUDA选择、独立gpu-1或强制物理GPU唯一准入。

当前网页视频任务的会话Pod尚未请求GPU，模型程序仍显式指定CPU。因此“节点与镜像已经支持CPU/GPU”已验证，但“网页视频任务已经自动使用GPU”尚未实现。后续只需在原B模式会话Pod中声明设备，并由模型层选择CPU/CUDA与可见设备编号、缓存所需模型会话；仍可由同一通用节点、同一容器完成。GPU共享不是阻碍后续接入的硬约束。

此轮是单服务器amd64仿真，非4台真实物理机或4块THOR验收。THOR官方BSP、ARM64依赖及真实车载网络仍需到位验证。设备选择限于容器已暴露的GPU；没有改变宿主机驱动或停止其他项目进程。
