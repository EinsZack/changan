# GPU视频推理与分段计时使用说明

日期：2026年11月10日。业务版本：0.5.2。代码、镜像与测试均在服务器维护。

## 正常使用

继续通过8310网页新建视频分析任务，选择原来的lab-1～4即可。每个参与节点为本任务创建一个通用容器，获得CPU、内存及该节点可用的GPU；模型在会话初始化时优先尝试CUDA。成功时保留同一个CUDA模型会话，连续处理后续分片。无法初始化CUDA时明确记录原因并改用CPU，不把回退结果标成GPU。任务结束后回收容器。

本轮没有新增GPU专用节点，没有增加任务提交时必须选择CPU/GPU的步骤。多个lab仍按已授权的仿真方式共享同一物理RTX 5090。视频解码、预处理、后处理与预览生成目前仍使用CPU。

## 在网页查看

1. 打开任务详情的“工作流与执行”，查看“启动与推理分段计时”。
2. 节点启动时间轴显示提交、调度、镜像拉取、容器启动、程序初始化、设备初始化、模型加载及预热。命中缓存时明确显示“镜像已缓存”，不虚构拉取区间。
3. 展开“启动阶段明细与设备”，查看实际后端、GPU名称/UUID、CUDA预热计算事件、模型加载次数和阶段时长。CPU回退会显示具体原因。
4. 展开一个分片，查看下载、视频分析、产物上传；视频分析下方单独绘制逐帧模型前向的实际区间，并列出解码、前后处理和预览的累计时长。
5. “容器与镜像”页仍可核查同一任务/节点的一个Pod处理多个分片，模型加载一次，任务结束后回收。
6. “历史与对比”选取同输入与参数的两次成功运行，新增实际后端、模型初始化、视频分析和模型前向对比。旧任务没有分段数据时显示“未采集”。

启动区间的Kubernetes事件时间精度可能为秒；细分时长采用单调时钟。跨物理机绘制同一绝对时间轴前需要同步节点时钟。未采集阶段保留空白，不以相邻事件猜出镜像下载时间。

模型前向的口径是ONNX Runtime的run调用返回CPU数组：GPU路径包括输入传入、计算和结果取回。它不是纯GPU内核计时，也不是完整视频分析时间。多节点的累计时长不等于任务墙钟耗时。分片时长截止于最终结果请求提交前，确认回执及平台最终聚合另计。

## 运维配置

配置写入服务器项目.env后重启API和内部网关，新任务才采用新配置；旧任务的冻结镜像/策略及旧结果保持原义。修改前确认没有在途任务。

| 配置 | 默认值 | 含义 |
|---|---|---|
| CHANGAN_MODEL_DEVICE | auto | 模型层尝试CUDA并记录成功或CPU回退；cpu/cuda供受控验证，cuda初始化失败则报错 |
| CHANGAN_MODEL_GPU_DEVICE_ID | 0 | 容器内可见GPU的索引，不是宿主物理索引6 |
| CHANGAN_VIDEO_IMAGE | 固定摘要 | 统一CPU/CUDA业务镜像，须与已验证源码对应 |

新应用快照版本3为统一运行环境预留至少2048 MiB主机内存，CPU与GPU对照都使用相同内存和CPU限制；会话预留、候选筛选和Pod限制一致。该值源自本服务器CUDA初始化超过旧1 GiB上限的实测，不能直接当作THOR最终参数。GPU内存池选项1 GiB仅限制ORT池，并非整个容器的显存硬配额。

普通任务不需要改模型策略。需要有控制的CPU/GPU实验时使用专用隔离验证实例和benchmark脚本，不手工更改正式任务元数据。

## 数据字段与复跑

- sessions[].workload.lifecycle：按Pod UID持久保存Pod创建、调度、镜像与容器启动证据；回收后仍可查询。
- sessions[].workload.startup_timing：程序导入、领取会话、模型初始化开始/结束和时长。
- sessions[].workload.inference_runtime：实际后端、执行提供程序、GPU身份、回退原因、模型加载/预热时长及CUDA实际计算证据。
- segments[].result.segment_timing：下载、分析、上传的单调时钟偏移及阶段时长。
- segments[].result.analysis_timing、frames[].timing：累计操作时长及逐帧前向区间。

模型就绪证据首次接受后冻结，重复回报只作幂等确认。服务器校验非负有限数、阶段顺序/范围、逐帧累计一致性和分片/会话后端一致性。旧记录无timing_version=1时保留原协议。

回归命令（项目专用环境）：

```bash
cd /root/projects/changan-orchestrator
/root/miniforge3/envs/changan-orchestrator/bin/python -m pytest -q
cd web
node --test tests/*.test.js
npm run build
```

CPU/GPU对照脚本为scripts/benchmark_gpu_timing.py，可靠性脚本为scripts/validate_timing_lifecycle.py，均拒绝连接正式数据目录。此次隔离目录为data/k3s-timing-validation，API8410/内部网关8411，同一K3s集群，实验时要求8310无在途业务。环境配置保存在隔离目录environment.json，使用该文件启动scripts/manage.py；不能仅改客户端数据目录而让后台仍连接正式数据。

对照使用准备完成且未分配的隔离任务冻结模型策略，再放开指定节点，避免切片写回元数据与实验配置竞争；不提供正式任务策略修改接口。--resume仅复用同一报告已完成的、核验实际后端正确的运行。

正式入口仍为SSH隧道转发8310。THOR、ARM64与真实车载网络尚未验证。
