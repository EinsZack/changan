# K3s任务内容器复用使用说明（0.5.0）

本版本按用户2026年11月8日的要求，把新视频任务从“每个分片一个容器”的A模式改为B模式。每个参与节点在一个视频任务内保留一个执行容器，模型加载一次，连续处理多个分片；整个任务结束或取消后回收。节点临时退出、Pod异常或执行超时才撤销异常会话并重新调度未完成分片。历史任务保留原来的执行证据。

## 日常使用

入口、视频上传、分片长度和调度算法设置均保持原有使用方式。通过SSH隧道访问服务器8310端口，创建任务即可采用B模式，无需逐节点启动worker。

```bash
ssh -N -L 127.0.0.1:8310:127.0.0.1:8310 -p 22031 root@10.13.0.9
```

打开任务详情的“容器与镜像”，先看“节点执行会话”，再看“分片执行记录”：

- 同一会话的多个分片应拥有相同Pod UID；普通24分片、4节点任务通常只有4个会话。
- 每个健康会话的模型加载次数为1，已处理分片数逐步增加。
- 单个分片完成后显示“分片完成，容器继续复用”，会话保留资源并等待后续分片。
- 整个任务结束后，会话从“回收中”变为“已回收”。业务结果完成和基础设施回收是两个独立状态。
- 故障恢复可能产生额外会话。旧会话及其Pod、失败分片、重试和清理状态均保留，不能只按会话数量判断是否复用。

若未指定节点范围，刚加入可执行集合且符合约束的节点，会在后续分片调度中参与；若明确选择了节点，只在指定范围内调度。节点按首次分配按需启动会话，不要求所有节点都准备好才开始推理。一次任务内每个节点最多一个会话、同时处理一个分片；不同任务不共享同一个业务容器。

## 运行和部署

业务工作区仍为服务器 `/root/projects/changan-orchestrator`，使用项目专用Python环境。

```bash
cd /root/projects/changan-orchestrator
source /root/miniforge3/etc/profile.d/conda.sh
conda activate changan-orchestrator
python scripts/cluster.py status
python scripts/manage.py status
python scripts/cluster.py kubectl get jobs,pods -n changan -o wide
```

Docker构建并推送应用镜像；业务容器由K3s的containerd运行。Job现在对应“任务＋节点＋一次会话”，不是一个分片。Job仍固定到调度选定的节点，业务重试由编排器管理；不启动节点常驻HTTP推理进程。

新服务器仍按[K3s部署与使用说明](K3s部署与使用说明.md)准备集群、网络、RBAC和模型资产。0.5.0镜像包含会话入口和用于旧任务兼容的分片入口。新任务默认且固定采用任务会话，旧任务的模式与镜像摘要不会被改写。

常规更新顺序：确认没有在途业务及待清理容器，备份SQLite和配置，拉取仓库，运行后端测试、构建镜像和前端，最后重启管理API与容器网关。运行中的任务已冻结镜像和模型摘要，不能只修改配置就宣称其已迁移。

## 生命周期与资源管理

| 对象 | 创建与复用 | 结束条件 |
|---|---|---|
| 任务 | 一段完整视频 | 全部分片结果有效，或失败/取消/超期 |
| 节点执行会话 | 任务首次向该节点分配分片时创建；保持模型和Pod | 任务结束，或节点/容器异常 |
| 分片尝试 | 每次分片分配或业务重试 | 结果及产物校验完成，或该次失败 |

模型加载阶段独立于推理：会话的Pod启动并认领身份后加载模型，回报就绪；随后领取分片。暂时没有分片时轮询等待，不退出容器。分片结果以数据库中的有效尝试和持久化产物为准，不再等待容器进程退出。每片处理后的临时输入和预览文件会从容器工作目录移除。

资源槽和内存按会话预留，不按已完成分片累加，也不会在分片完成后对其他任务释放。同一任务调度时可复用自己已占用的槽位；其他任务仍能看到该槽被占用。当前每个逻辑节点一个槽。任务越多时会排队，尚未实现空闲会话的跨任务抢占或跨任务模型共享。

已有外部资源池适配器按会话ID作为预留幂等键，申请到任务截止时间之后300秒的租约，确认容器清理后释放。这个接口只有契约测试，尚未与顾强强的正式资源池联调；正式接入仍需确认租约最大时长、续约和失联隔离规则。

## 异常与恢复

- 管理API或内部网关短时重启：会话、当前分片和结果都持久化；恢复时读取现有Job/Pod身份，继续使用原容器。最终回执丢失时，同一结果重发只确认一次，不重复计数。
- 普通分片错误：记录失败、按重试上限重排；健康会话继续使用。已完成的分片不重跑。
- 节点退出、会话心跳超时、Pod中断或分片执行超时：先撤销旧会话的执行权，再将未完成分片交给可用节点。旧Pod的回调不能提交结果。已断联设备可能暂时仍在计算，但不会被当作有效结果来源。
- 失联节点的资源槽保持隔离，直到Kubernetes对象清理且有实际终止证据，或节点恢复后可确认清理。不会把强删API对象当成设备已停止。
- 执行容器每2秒报告心跳；与网关失联超过约20秒会自行停止继续处理，服务端超过30秒判定会话超时。该时间不是硬实时承诺，仍受请求超时、推理调用与调度周期影响。
- 模型/容器准备受 `min(180秒, attempt_timeout)` 限制；分片的 `attempt_timeout` 从实际领取时开始计算，复用容器的总存活时间不受单片超时限制。任务截止时间仍是整体上限。
- 容器不持有Kubernetes管理凭据。会话令牌绑定Pod UID和Job/节点身份；分片另有独立尝试令牌。上传产物不可更改，重复上传相同摘要可幂等确认。

## 开发与验证入口

核心代码：`app/session_execution.py`管理会话、分配、认证和结果提交；`workers/container_entry.py`实现加载一次模型后的分片循环；`app/container_execution.py`保留旧任务兼容及共用输入/产物接口；`app/kube.py`生成会话Job；`app/engine.py`衔接调度和聚合；`web/src/ContainerExecution.jsx`展示复用证据。

数据库新增 `execution_sessions` 和 `attempts.session_id`，采用增量迁移；任务详情和导出新增脱敏 `sessions` 列表。内部新增 `/internal/sessions/{id}/claim|ready|heartbeat|next`，既有分片下载、产物上传及事件接口继续使用独立的分片令牌。

```bash
TMPDIR=/dev/shm python -m pytest -q
cd web
npm run build
npx playwright test -c playwright.k3s.config.js
```

`TMPDIR=/dev/shm`仅加速可丢弃的测试数据库，实际业务数据库仍在项目data目录。真实集成测试和A/B基线只允许运行在 `data/k3s-validation`、8410/8411的隔离实例：

```bash
export CHANGAN_DATA_DIR=/root/projects/changan-orchestrator/data/k3s-validation
export CHANGAN_PORT=8410 CHANGAN_PUBLIC_BASE=http://127.0.0.1:8410
export CHANGAN_CONTAINER_PORT=8411 CHANGAN_CONTAINER_BASE=http://172.29.1.1:8411
export CHANGAN_SKIP_REDIS=1
python scripts/manage.py start
python scripts/integration_sessions.py --faults
python scripts/benchmark_sessions.py
```

内部网关地址示例仅用于当前开发集群。`--faults`会操作本项目K3s逻辑节点，运行前必须确认正式实例无在途任务；脚本会检查并恢复临时移除的节点标签和暂停的agent。性能对照顺序运行，使用同一镜像、模型、视频、CPU限制和参数；A使用镜像内保留的旧分片入口，B使用会话入口。

## 当前验证边界

当前为同一服务器上的4个K3s逻辑节点、amd64镜像和CPU ONNX推理。4块THOR、ARM64镜像、NVIDIA GPU运行时与实际车载网络仍待实机接入。B方案减少容器启动、模型加载和回收频次，但推理CPU配额、视频切分、数据传输及服务器负载仍会影响总耗时，不能把服务器对照结果直接作为车端性能指标。
