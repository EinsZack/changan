# 双Thor平台部署与使用说明

更新时间：2026年11月13日。现已接入Thor1、Thor2两个真实执行节点。

## 日常使用

Mac保持在板卡所在的192.168.50.x局域网，当前地址192.168.50.231。打开`http://127.0.0.1:8310/?release=20261113-thor2`。

新建分析任务的执行范围选“全部可用节点”，当前会使用Thor1、Thor2；也可选择“仅thor1”或“仅thor2”建立单节点任务。选择资源与网络感知或可行节点轮询。复现本轮双板场景使用24秒内置测试视频、1秒分片、10fps采样。

在任务详情查看：

- 工作流与执行：两行实际节点时间轴、每片实际落点、CUDA及分段计时。
- 容器与镜像：2个节点会话、模型共加载2次、每个节点各1次；结束后已回收2/2。
- 分析结果：24/24分片、240采样帧、完整覆盖率及真实识别预览。
- 调度决策：候选快照、过滤与实际选点。

只关闭SSH终端不需要重启平台或板卡服务。任务执行依靠Mac后台平台和板端systemd服务，SSH用于运维。

## Mac重启后的启动

Mac继续使用已有Miniforge项目专用环境`changan-platform`，没有安装容器引擎。登录用户会话后执行：

```bash
source /opt/homebrew/Caskroom/miniforge/base/etc/profile.d/conda.sh
conda activate changan-platform
python "/Users/eins/Library/Application Support/ChanganPlatform/current/scripts/install_native_services.py" \
  --root "/Users/eins/Library/Application Support/ChanganPlatform" \
  --env-prefix "/opt/homebrew/Caskroom/miniforge/base/envs/changan-platform" \
  --gateway-host 192.168.50.231
```

脚本可重复调用，已运行的服务会复用。API/网关仍由当前用户会话后台启动，没有故障自动拉起；Redis、Zot及防空闲睡眠服务使用LaunchAgent。caffeinate不保证合盖后持续联网。

## 板端服务与SSH重连

Mac公钥已授权到两板，普通运维可免密连接：

```bash
ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 thor1@192.168.50.151
ssh -o ServerAliveInterval=30 -o ServerAliveCountMax=3 thor2@192.168.50.152
```

上述保活参数可维持/检测SSH连接，断线后重新运行SSH命令即可。无需常开这两个终端。

Thor1为K3s server兼执行节点，Thor2为agent；服务均由systemd管理。本轮已验证Thor2服务重启后恢复，物理重启尚未测试。

在对应板卡查询：

```bash
# Thor1
systemctl is-active k3s
sudo k3s kubectl get nodes -o wide

# Thor2
systemctl is-active k3s-agent
systemctl is-enabled k3s-agent
sudo journalctl -u k3s-agent -n 50 --no-pager
```

只有相应服务异常时，再在空闲时段重启对应服务：

```bash
# 在Thor2
sudo systemctl restart k3s-agent
# 在Thor1
sudo systemctl restart k3s
```

Thor1承载集群控制面，重启它会暂时影响调度；不要在普通SSH会话断开时直接重启整个集群。

## 断联排查顺序

1. 在Mac执行`ipconfig getifaddr en0`，确认当前仍为192.168.50.x。11月12日曾查到Mac切至192.168.2.179，导致旧的192.168.50.151及Mac网关地址均不可达；当时证据不能证明Thor因SSH空闲而休眠。
2. 执行`ping -c 3 192.168.50.151`、`ping -c 3 192.168.50.152`，以及`nc -vz -G 3 192.168.50.151 6443`、`nc -vz -G 3 192.168.50.152 22`。SSH和6443都超时应先检查网络、路由器和板卡供电。
3. 网络恢复后重新SSH查询服务；Thor2使用`k3s-agent`，Thor1使用`k3s`。
4. 网页本身打不开时，先按上面的Mac启动命令恢复API/网关；网页可开但节点离线时检查节点服务及Mac到6443的连通性。
5. 节点恢复后确认网页两节点在线，再提交一个小任务。必要时导出任务证据，勿删除历史数据库或重装集群作为首选修复。

当前没有配置路由器固定DHCP租约。Mac、Thor地址变化时，需要检查网关绑定、仓库地址/证书、各节点仓库CA配置及K3s控制面地址，不能只改SSH地址。

## 命令行复跑完整验收

在无其他在途任务时，使用项目专用环境执行：

```bash
python "/Users/eins/Library/Application Support/ChanganPlatform/current/scripts/validate_thor_cluster.py" \
  --root "/Users/eins/Library/Application Support/ChanganPlatform" \
  --nodes thor1 thor2 \
  --output "/Users/eins/Library/Application Support/ChanganPlatform/data/evidence/thor-dual-recheck" \
  --cancel
```

该脚本真实上传演示视频并新增4条任务：Thor2单板、两种双板算法、双板运行中取消。输出目录不要复用需要冻结的旧证据。脚本要求两个节点身份不同、Ready、各有1个GPU，且业务命名空间无在途工作；不会人为改写成功状态或吞吐。

只验证Thor2可使用：

```bash
python "/Users/eins/Library/Application Support/ChanganPlatform/current/scripts/validate_thor_native.py" \
  --root "/Users/eins/Library/Application Support/ChanganPlatform" \
  --node thor2 --expect-backend cuda
```

原单板脚本沿用首轮证据目录，会更新其最近任务指针；需要保留新一轮完整证据时优先使用带独立`--output`的双板验收脚本，并只传`--nodes thor2`。

## Thor2配置与后续节点接入

Thor2部署配置：

- `/etc/rancher/k3s/config.yaml`：server为Thor1的6443，node-name为thor2，node-ip为192.168.50.152，flannel-iface为wlP1p1s0。
- `/etc/rancher/k3s/agent-token`：root所有、600，仅供加入集群，不在终端展示或拷入文档。
- `/etc/rancher/k3s/registries.yaml`与`mac-registry.crt`：信任Mac仓库CA。
- `/var/lib/rancher/k3s/changan-cache/cuda`：UID/GID10001、700。
- 节点标签：`changan.io/node-id=thor2`、`physical-host=thor2`、`kind=vehicle`、`slots=1`、`memory-mib=65536`（各项均在`changan.io/`前缀下）。
- 板卡序列号SHA256注解和Kubernetes节点UID用于物理身份核对；本轮两板的GPU UUID相同，不能拿GPU UUID计数物理板。

下一板先核查L4T/驱动、架构、设备组、网络及独立硬件身份；复用已校验离线K3s文件，使用新node-name/node-ip加入为agent，配置仓库CA和节点本地缓存。先运行普通GPU Pod，确认实际CUDA后再加业务注册标签，最后执行单板与多板真实视频验收。不要复制Thor1的server数据目录或Thor2的节点身份目录。

镜像继续使用已验证的runtime3不可变摘要，GPU附加组44/993及index设备策略按实际设备权限核查。软件源正常时维持原配置。本轮接入没有修改板端软件源。
