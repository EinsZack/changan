# 车群算力池任务编排调度与协同执行开发计划

编制日期：2026年9月23日  
面向人员：车群算力池共享方向中负责任务编排、调度算法与协同执行的开发者  
依据文件：[算力共享关键技术研究及原型开发技术要求 9.5](../references/原始本地资料/算力共享关键技术研究及原型开发技术要求-9.5.docx)

## 1 结论与个人负责范围

建议将本人负责的子系统正式命名为 **车群算力池任务编排调度与协同执行子系统**。它接收另一位同学提供的可调度资源信息，把业务任务转化为可执行的工作流和子任务，完成节点选择、任务下发、执行跟踪、异常处理和结果聚合，并向用户展示全过程。

本人负责范围的核心对应原文表1第26—38项“算网编排与任务闭环”，同时承担第15项全局调度决策、第16项调度控制成功率的主要实现，以及表2第2场景中视频切分、任务调度、车端分析执行和多源结果聚合的业务链路。资源池同学主要负责资源接入、采集、池化和基础设施管理。两人的交界是“资源是否可调度”和“调度决定如何落到真实节点”。

这里的“三个部分”是按三人实际分工形成的工作包，不是甲方原文正式划分的三个独立交付项目。原文也未逐项指定学生负责人，以下责任归属属于建议分工，需要在组内形成一致口径。

中期建议交付一个可以在真实车端节点上运行的 **多车协同视频分析与任务调度原型**：输入一段交通或园区视频，切分为多个片段，依据节点资源和网络状态分配到车群节点，完成行人及车辆识别、回传和聚合，并在网页中实时展示工作流、调度依据、执行节点和结果。中期先把这一条链路做实，再逐步补齐通用编排平台功能。

本文使用三类表述区分依据：**原文要求**是甲方文件明确写出的事项；**建议实现**是面向个人工作量的技术拆解；**待确认**表示分工、测量口径或原文存在歧义，不能自行视为已获甲方认可。本文提出的中期增强展示不等于新增合同指标。

**需要主动划清的两个交叉点：**

1. 表1第20项 Job/CronJob 管理属于底层任务资源管理；第35项调度策略属于业务工作流触发。建议底层 Job/CronJob 由资源池同学管理，本人维护工作流运行记录和调度策略。若用 CronJob 触发工作流，应只保留一个实际触发源，防止重复执行。
2. 第34项“调度算法管理”和第39—46项“算法应用生命周期管理”不是一套功能。前者管理节点选择逻辑，后者管理应用市场、版本、镜像、Chart、部署和实例。不能因都叫“算法”就全部划给本人，也不能漏掉应用市场这部分项目要求。

原文第1.4节要求乙方团队不少于9人，与目前三位主要开发者的实际安排存在组织口径差异。应由导师或项目负责人确认三人是否属于更大的承诺团队；不将资质、团队配置和全部项目成果指标计为本人独立交付责任。

## 4 中期验收范围与建议交付

### 4.1 中期原文明确要求

截止时间为 **2026年11月30日**。第2.5节表5要求车群原型初版提交车群算力池化技术实施方案，展示不少于4个节点的在线状态、资源状态与算力池资源视图初版。表7还要求原型提供方案、界面及关键功能演示视频或录屏，硬件连接图与接口说明，源码初版与部署脚本，并通过内部评审形成会议纪要。

项目级中期成果另包含不少于2篇通过长安及代理评审的专利技术交底书，以及1份通过长安评审的中期技术可行性报告。这些应分解给团队，不能默认由本人独立完成全部数量。

表5没有明确要求中期完成表1全部通用平台功能、完整视频处理场景或全部性能指标。因此，中期不宜以一次性做完通用工作流平台为开发目标。不过，只有资源看板难以证明本人的任务编排和调度工作，建议额外交付下面的可运行链路。

**时间冲突处理：** 表5要求中期报告随11月30日前中期验收完成，表6 T3却将初版可行性报告列为12月31日。建议内部按11月30日前报告已具备评审条件准备，负责人书面确认最终口径；不能自行按较晚日期顺延。

### 4.2 中期系统建议

建议名称：**车群协同视频分析任务调度原型**。

部署由1个管理调度节点和至少4个真实车端算力节点构成。管理侧提供工作流运行、算法选择、任务调度、结果聚合和网页展示；车端运行分析任务。管理节点的硬件类型由甲方与组内确认，不能将其计入4个车群算力节点。两异构集群属于最终明确指标，建议尽早落实；若中期尚未完成，应在阶段报告列明差距。

建议选用一段固定交通或园区视频，切成若干时间片段，片段数大于节点数，便于观察连续分配与负载变化。片段长度、分辨率、模型和推理批大小先通过目标板卡实测确定，避免以开发机能力推定车端能力。

中期主流程如下：

```mermaid
flowchart LR
    A[提交视频与任务条件] --> B[切分视频并生成子任务]
    B --> C[读取资源池快照]
    C --> D[过滤候选并运行调度算法]
    D --> E[预留资源并下发任务]
    E --> F[多个车端节点并行分析]
    F --> G[状态与结果回传]
    G --> H[聚合结果并生成报告]
    F --> I[失败或节点失联]
    I --> J[核对执行状态与重试条件]
    J --> C
```

建议将正常执行、受控负载变化、一个执行节点中断三种演示准备好。故障演示是中期增强项，应在正常闭环稳定后加入，不得牺牲基本可复现性。

## 5 中期可视化页面设计

采用一个统一网页入口，由资源池同学维护资源页，本人维护任务、工作流、调度和结果页。重点是让评审能够验证“为什么选这个节点、是否真的在该节点执行、最终得到了什么”。

| 页面 | 展示和交互 | 数据来源 | 评审证据 |
|---|---|---|---|
| 车群资源总览 | ≥4节点、集群归属、在线健康、可用/占用资源、网络、最近更新时间 | 同学的资源服务 | 在线状态与现场板卡一致；不可用指标显示不支持或无数据 |
| 任务提交 | 视频选择、片段参数、模型、资源需求、优先级、截止时间、算法策略 | 任务服务 | 提交后产生真实task_id及输入记录 |
| 工作流运行 | 有向图显示各步骤等待、运行、成功、失败；点击节点看输入输出与日志 | 工作流事件 | 算法节点真实接收资源快照并输出目标节点 |
| 调度决策详情 | 候选列表、过滤原因、评分项、目标节点、实际执行节点、决策耗时 | 调度记录及执行回执 | 决策与执行落点一致，失败重选有新记录 |
| 多节点执行看板 | 片段到节点的分配、运行时间轴、进度、重试次数和节点吞吐 | 执行事件和心跳 | 能看见至少多个节点同时处理不同片段 |
| 视频分析结果 | 原视频时间轴、识别框预览、每片段行人/车辆统计、完成覆盖率和输出下载 | 车端产物及聚合服务 | 输出能反查到片段、节点、模型和运行批次 |
| 历史与对比 | 运行检索、日调用次数、成功率、基线与新算法耗时、数据导出 | 持久化运行记录 | 页面统计与原始记录可逐项核对 |

页面布局建议：上方显示任务及运行状态，中间左侧放工作流图、右侧放候选节点与选择依据，下方放分片执行时间轴和日志；结果页独立展示分析产物。资源占用、任务吞吐和端到端耗时应分开，不使用含义不明的“总算力百分比”替代不同芯片资源。

所有动画和进度必须来自实际事件。开发期模拟节点、注入的网络状态、录像回放必须明确标识；无法获取细粒度推理进度时，只展示阶段状态或已完成片段数，不制作伪进度。安全凭据和Secret不进入节点入出参展示。

### 5.1 建议的现场演示脚本

1. 展示节点清单、实物编号、4个节点在线和当前资源状态，说明管理节点与算力节点区别。
2. 提交固定视频，展示切片列表和任务资源条件。
3. 查看一次调度决策的输入、候选排除原因和目标节点，再进入实际节点日志核对。
4. 展示多个节点并行分析、片段逐一完成和结果聚合，打开至少一个真实输出。
5. 用相同业务参数分别运行基线和资源感知策略，展示原始结果及差异；若提升不明显，如实解释通信和切片开销。
6. 有余量时注入单节点失联，展示新任务避开该节点，以及在途任务核对、超时和重试过程。
7. 打开历史记录，导出本次执行证据，再展示周期触发实例与其策略关联。

建议准备一次完整录屏及可复现操作说明，作为现场之外的审查材料；录屏不替代真实硬件执行要求。

## 6 系统模块与开发顺序

### 6.1 模块划分

| 模块 | 本人要实现的内容 | 与对方的边界 |
|---|---|---|
| 业务任务服务 | 任务描述、输入管理、切片计划、子任务表和聚合状态 | 不承担节点发现 |
| 工作流运行器 | 模板解析、依赖检查、节点执行、参数映射、超时和运行记录 | 调用平台能力适配接口 |
| 调度服务 | 资源过滤、算法调用、候选解释、分配方案与重选 | 只通过统一资源接口读取和预留资源 |
| 执行适配层 | 调度决定转为底层运行请求，关联平台执行ID | 由对方提供Job或其他执行后端；双方联调 |
| 视频分析执行组件 | 接收片段、调用模型、进度/状态和结果回传 | 节点基础运行环境和驱动由对方协调 |
| 聚合服务 | 输出校验、片段排序、去重、统计、文件索引和完整性判断 | 依赖约定的数据存储与传输方式 |
| 追踪和查询服务 | 运行事件、图形轨迹、日志检索、统计与导出 | 可复用共同日志基础设施 |

建议中期先做“模块清楚、部署简单”的服务组合，不以拆分大量微服务作为完成度。工作流先支持有向无环依赖、参数传递、条件失败和并行子任务；循环、复杂分支或任意用户代码能力只在验收需要明确后扩展。

原文第2.1节不限定技术栈，允许容器、轻量进程或等效方式；但表1又具体列出多种容器与集群资源。节点执行方式可以按硬件选型，不能据此删掉整个平台的最终功能要求。第三方基础软件仅是底座，仍需交付车端适配、资源采集、任务下发、监控及接口等自研或定制成果。

### 6.2 工作流与业务逻辑的关系

推荐模板为：接收任务 → 校验输入 → 切片 → 获取资源快照 → 调度算法 → 平台能力下发 → 等待子任务 → 聚合 → 保存结果。

API节点用于读取平台能力或外部接口；Redis节点可读写一次演示状态；脚本节点处理输入或输出；算法节点选执行位置；平台能力节点实施任务下发。Redis在演示中真实读写即可，不必为了凑五类节点把关键任务状态只放入缓存。Kafka作为后续事件触发方式补齐。

“调度算法节点”输出分配建议，“平台能力节点”执行该分配，两者职责分开。底层平台若不能按指定节点执行，应返回失败或重新调度，不能由底层静默随机分配后仍显示上层原决定。

## 7 调度算法实现计划

### 7.1 中期先完成可解释的基线与改进策略

建议实现两套可切换策略：

- **可行节点轮询基线**：先满足硬约束，再在可行节点中轮询。用于验证平台闭环与提供公平比较。
- **资源和网络感知策略**：在可行节点中综合预计完成时间、传输开销、队列负载和状态风险选择节点。任务优先级影响队列顺序，截止时间影响是否接纳及选点。

硬约束包括在线与健康、资源快照新鲜度、处理器架构、运行时和模型支持、可用内存/显存、已占用及已预留资源、必要节点标签、位置约束和输入数据可达性。CPU/GPU/NPU不能用同一“算力分数”直接互相替代，缺少某类加速器或模型运行时的节点应按兼容性规则过滤。

一个可解释的起步估计式为：

`预计完成时间 = 队列等待时间 + 输入传输时间 + 本片段预计计算时间 + 结果回传时间`

其中计算时间由“节点 × 模型 × 分辨率”的实测吞吐估计，传输时间由数据量和有效带宽估计。缓存命中和并发竞争会影响估计值，应记录误差。位置可作为限制或距离成本输入；不适用的位置条件不强行参与打分。温度或可靠性惩罚是建议扩展，不属于原文指定算法公式。

批量分配多个片段时，每分配一个片段就更新计划中的队列和资源预留，避免所有片段根据同一份空闲快照集中到一个节点。候选为空时返回明确失败原因或在有界等待后重试，不进行无限调度循环。

### 7.2 中期后算法研究方向

在基础策略稳定后，研究动态视频切片、异构节点速度估计、网络与计算联合优化、离线风险感知、多优先级任务和在线重调度。根据实测瓶颈选择一个主要创新点，不预先承诺必须使用强化学习、复杂优化求解器或大模型。

甲方最新版场景的明确业务是视频分析，没有要求采用大模型驱动调度、跨车拆分大模型或分布式模型训练。因此不把这些内容作为本人本期必做任务。

### 7.3 指标测量与对比方式

| 测量对象 | 建议记录口径 | 注意事项 |
|---|---|---|
| 决策延迟 | 从一次全局分配请求进入调度服务到形成可提交分配方案的时间 | 包含输入准备和候选查询的范围需确认；≤10s是原文指标，不能只量打分函数 |
| 调度成功率 | 在预设截止时限内达到约定调度成功状态的任务数 / 纳入测试的调度任务总数 | 原文未明确定义成功状态；须确认是接收、启动还是完成，不与业务推理成功率混用 |
| 业务完成率 | 成功完成全部必要片段并完成聚合的业务任务比例 | 缺片不能计为完整成功 |
| 端到端耗时 | 提交接受至完整结果可获取 | 含切片、排队、传输、执行、聚合；冷启动与预热状态分别记录 |
| 协同加速比 | 同等输入和结果要求下的单节点耗时 / 多节点耗时 | 指明单节点硬件和基线，不承诺线性加速 |
| 故障恢复 | 故障发现、重新分配、替代执行开始、任务完成等时间戳 | 与第25项节点接入恢复≤3min分开统计 |

建议每次比较固定视频、模型版本、阈值、分辨率、节点范围和网络条件，并保存配置。先用小规模重复运行排查误差，再对正常、资源紧张、节点失联、带宽下降、并发提交等条件分组测试。最终≥99%的检验样本量、任务分布、截止时限、失败归因及是否允许重试应形成确认后的测试方案；几次成功演示不足以证明长期成功率达标。

## 8 协同执行与数据正确性

### 8.1 视频任务如何分解

初版优先按时间片段切分一段视频，每片段可独立推理。记录原视频ID、片段序号、起止时间、帧范围、分辨率、模型版本和输出格式。切片边界尽量选择可解码位置，必要的重编码时间纳入总耗时。

聚合输出建议包含片段完成列表、识别结果时间轴、抽样带框图像、逐帧或逐片段统计及机器可读结果文件。中期可采用帧级目标数或目标出现次数统计，不将简单加总描述为“唯一行人数”或“唯一车辆数”。若要统计不重复对象，需要明确跟踪ID、跨片段去重和边界处理；重叠片段也必须消除重复统计。

任务结果至少保留任务、片段、执行节点、执行尝试、模型版本及时间信息。聚合服务验证所有必要片段完整，并按有效尝试选择结果。后续“行人玩手机识别”在表2中是可扩展应用，不是本期必须与基础行人车辆分析同时实现的独立功能。

### 8.2 状态机与异常处理

建议子任务状态：`PENDING → DISPATCHING → ACCEPTED → RUNNING → SUCCEEDED / FAILED / TIMED_OUT / CANCELED`。父任务只有在必要子任务完成且聚合成功后进入SUCCEEDED。重试创建新的attempt_id，保留原尝试记录。

必须覆盖下列行为：

- 调度前节点离线或资源不足：过滤该候选并记录原因。
- 调度后资源已被占用：预留或提交失败后重新读取资源并重选。
- 下发请求超时：先按幂等键查询是否已经接收，不能直接产生重复执行。
- 执行中失联：标记状态未知，经过约定超时与状态核对后决定重试；不立即把节点上仍在运行的任务当成停止。
- 结果重复或旧尝试晚到：依据attempt_id和有效执行令牌去重，避免覆盖新结果。
- 片段失败或父任务取消：记录部分完成情况，停止继续派发，按策略取消其余任务并释放资源。
- 管理服务重启：从持久化记录重建在途任务，与执行端核对，不依赖内存中的工作流状态。

对于视频分析这类可重复执行任务，可使用至少一次执行加结果幂等；不宣称实现了未经验证的严格一次执行。中期可以限制自动重试次数和任务类型，以减少异常复杂度。

## 9 与资源池同学共同冻结的接口

下面是建议接口契约，不代表对方已经实现，也不预设现有技术栈。

| 接口能力 | 建议主要字段 | 提供方 | 本人使用方式 |
|---|---|---|---|
| 节点及资源快照 | cluster_id、node_id、架构、运行时、加速器、可用/占用/预留资源、标签、位置、健康、网络、观测时间、快照版本 | 资源池同学 | 候选过滤与算法输入 |
| 节点状态事件 | 节点、状态变化、发生时间、事件序号 | 资源池同学 | 避开失效节点，触发任务核对 |
| 资源预留和释放 | node_id、需求、租约、任务ID、快照版本、失败原因 | 双方共同，对方实现资源侧 | 防止并发重复分配；提交失败释放预留 |
| 任务执行提交 | task_id、subtask_id、attempt_id、幂等键、目标集群/节点、制品版本、输入地址、资源需求、超时、执行令牌 | 本人定义协议，对方或共同执行适配层承接 | 将算法结果转为可核验的真实执行 |
| 执行查询和取消 | execution_id、实际node_id、状态、退出码、日志地址 | 共同执行适配层 | 状态核对、取消、恢复和历史查询 |
| 事件与结果回传 | 全链路ID、事件序号、状态、进度、时间、结果地址、错误码 | 本人执行组件 | 推动工作流和结果聚合 |
| 制品与数据访问 | 模型/镜像/脚本版本、架构、输入输出位置、校验值、访问方式 | 双方共同 | 保证任务在选中节点可运行、可取数和可回传 |

接口必须统一单位，例如内存用字节、带宽明确bit/s或byte/s、延迟用毫秒。快照时间与调度时间分开记录；跨节点时间使用共同校时方案，测量本地耗时使用可靠的本地时钟。

为独立推进，可先用相同契约实现本地资源服务替身及测试执行端，但必须标记模拟模式。联调时只替换适配层，业务工作流与算法保持不变。至少提前两周切到真实资源服务和真实车端，避免临近中期才发现接口或运行时不兼容。

共享前端导航、账号、集群及节点标识、统一错误码、日志保留方式、数据目录和部署脚本也应提前商定。建议由本人维护任务运行状态的唯一事实来源，对方维护资源和集群状态的唯一事实来源，前端通过双方接口展示，避免两边各存一份互相矛盾的任务状态。
