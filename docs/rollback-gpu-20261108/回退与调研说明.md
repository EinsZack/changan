# 0.6.0回退与通用节点CPU/GPU容器调研

2026年11月8日。根据用户要求，先撤回0.5.1→0.6.0迭代，再研究现有K3s节点的GPU接入。本轮没有实施新的通用GPU执行架构。

## 结论

**K3s支持在同一个普通算力节点上部署同时使用CPU和GPU的容器，不要求另建一种“只能调用GPU”的节点。** CPU、内存和GPU都是节点资源，GPU运行时和设备插件负责把获分配的设备交给业务Pod。GPU能力属于节点资源配置，不是互斥的业务节点类型。

**但回退后的现有四个节点还不能直接让普通业务容器使用GPU。** 外层k3d节点可见设备文件，内层业务Pod没有设备与驱动注入；这两层必须区分。安装含CUDA的业务镜像本身不足以打通这一链路。

上一轮0.6.0选择“保留四个CPU节点，新增gpu-1，任务级固定CPU/CUDA”的实现，与用户要求的通用节点及通用容器不一致。新增gpu-1在技术上也能运行CPU，并非K3s要求的GPU专用类型；问题在上一轮部署和应用约束的选择。

## 普通Pod隔离检查

在原`lab-1`创建了临时普通Pod，使用已缓存仓库中的CUDA依赖镜像，不申请GPU、不设特权、不挂载宿主设备；以UID 10001、只读根文件系统运行。该镜像来自上一轮保留的构建产物，仅用于诊断，正式业务仍使用回退后的CPU镜像。

- 镜像可枚举CUDAExecutionProvider和CPUExecutionProvider。
- Pod内没有`/dev/nvidia*`设备。
- 加载`libcuda.so.1`失败，报缺少共享库。
- 同一个Pod用CPUExecutionProvider成功执行YOLOX模型，输出形状为`[1,3549,85]`。

这验证了“镜像包含CUDA支持”与“容器具备实际GPU访问条件”的区别。**本轮没有完成原四节点的GPU运行时升级，也没有声称这些节点已经通过GPU计算验收。** 临时Pod和独立命名空间已删除。清单、实际Pod状态和输出分别保存在`ordinary-pod-manifest.json`、`ordinary-pod.json`和`ordinary-container-probe.json`。

## 满足用户目标的接入方向

1. **保持统一节点身份。** 节点都报告CPU、内存、GPU等资源。服务器可以沿用原四个逻辑节点；将来每块THOR是一个物理CPU/GPU节点。无需为GPU能力额外新增业务节点类型。
2. **补齐同一节点的运行环境。** 现有k3d是嵌套容器环境，需在节点层提供匹配宿主驱动的库、NVIDIA Container Toolkit以及K3s/containerd运行时配置。k3d官方提供支持CUDA的节点基础镜像路线；它仍是能运行CPU和GPU负载的通用节点环境。是否重建原节点及身份/卷保留步骤应在后续实施前验证。
3. **统一业务镜像能力。** 同一架构的镜像同时包含CPU/CUDA推理支持。CPU和GPU可以由同一个业务容器使用；实际执行后端由应用策略决定并回报证据，不把整个业务节点划成只能用某一种计算资源。
4. **在创建会话时分配资源。** 按标准设备插件方案，Pod同时申请CPU、内存和所需GPU；运行时将获分配的GPU暴露给它。获分配GPU后，容器仍可执行CPU代码及CPU推理。单纯把RuntimeClass命名为nvidia不代表容器只能用GPU。
5. **保留B模式。** 一个任务在节点上的容器持续处理多个片段，模型可按实际后端缓存。CPU/GPU选择不应重新退回“一片段启动一个容器”。

服务器多个逻辑节点共用一台物理机。后续若将四个逻辑节点都升级为GPU可用，必须确定不重复计算的设备分配或明确的共享策略；不能让每个节点把同一张卡都上报为独占可用。多个容器共享一张GPU与“同一容器支持CPU/GPU”是两个独立问题，后者并不要求先实现前者。

板卡到位后优先在每块真实THOR上部署K3s Agent和匹配官方系统的NVIDIA运行环境，业务镜像按实际架构/BSP适配。服务器k3d的嵌套适配不直接复制为板端部署步骤。

## 官方依据

本次已在线读取以下一手资料，访问记录与页面摘要校验见`sources.json`。示例中的版本仅作机制说明，不直接作为本项目安装命令。

- [K3s：替代运行时与NVIDIA Container Runtime](https://docs.k3s.io/advanced#nvidia-container-runtime)：启动时发现已安装的NVIDIA运行时；未设置为默认运行时时，Pod通过RuntimeClass选择。
- [Kubernetes：Schedule GPUs](https://kubernetes.io/docs/tasks/manage-gpus/scheduling-gpus/)：GPU由设备插件登记为节点资源，容器通过资源请求获得；并未规定GPU节点不能运行CPU工作负载。
- [k3d：Using NVIDIA GPUs](https://k3d.io/v5.8.3/usage/advanced/cuda/)：解释嵌套节点所需的运行环境、设备插件和CUDA测试；支持GPU的节点镜像不等于GPU专用业务节点。
- [NVIDIA Container Toolkit安装与containerd配置](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)：GPU容器需要宿主驱动和容器运行时配套。K3s应结合其专用containerd配置方式，不能直接照抄独立containerd服务命令。
