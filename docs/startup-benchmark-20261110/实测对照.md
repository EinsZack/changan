# 多容器视频任务启动优化实测对照（2026年11月10日）

环境：开发服务器，四个lab逻辑节点（k3d）共享同一张RTX 5090，驱动590.48.01，镜像`video-unified@sha256:19f97fb5…`，CUDA自动策略。任务均为正式8310服务、演示视频24秒/10fps、1秒分片、请求15fps、资源感知调度，每次共24片240帧。各次任务之间等待会话回收，每个任务都新建4个Pod。服务器上的其他应用没有停止，结果只代表本开发环境，**不能作为THOR实机结论**。

脚本：`scripts/benchmark_startup.py`，提交任务后从持久记录读取时间轴（相对任务started）。原始结果见本目录各JSON。

## 结果

| 阶段 | 累计改动 | 各次端到端/s | 中位/s |
|---|---|---|---:|
| A 基线0.5.2 | 无 | 75.65 / 85.85 / 67.03 | 75.7 |
| B | +未下发片段改派 | 54.29 / 74.24 | 64.3 |
| C | +SQLite synchronous=NORMAL、模型摘要缓存 | 52.71 / 66.57 | 59.6 |
| D | +派发与维护分为两个循环、WAL常驻连接 | 41.88 / 38.09 | 40.0 |
| E | +节点持久CUDA缓存（逐节点自然积累） | 49.08 / 29.48 / 28.21 / 29.55 | 29.5 |
| F 最终 | +缓存seed、控制面停顿容忍 | 47.70 / 26.09 / 25.72 | **26.1** |

所有计入的任务均为24/24片、240帧、重试0，没有attempt_failed等故障事件。

**基线（A）**：每次都有部分节点首次CUDA前向耗时56～61秒（另一部分约11秒）。快节点承担了大部分片段（片数分布19/1/3/1、6/6/7/5、1/1/10/12），尾部要等慢节点。

**最终（F）**：四节点warmup为0.40～1.15秒，就绪时间+7.4～+10.7秒，片数分布6/6/6/6、6/7/6/5，最后一片约+25秒完成。F的首次（47.7秒）是服务重启后紧接着运行的，认领阶段偏慢（+16～+24秒），与当时宿主IO较忙一致。按全部三次计，中位仍是26.1秒。

## 每项改动的依据

1. **CUDA持久缓存**（E阶段，影响最大）
   - 冷缓存时首次前向会编译约15 MB的内核（约11秒），有时还会额外编译约75 MB（约50秒，集中在Add_59）。走哪条路径不确定，所以一次预热可能只缓存到小的那部分。
   - 节点缓存积累到完整的约91 MB后，跨Pod的warmup稳定在0.4～1.2秒。证据：同一节点4进程×3轮均≤1.8秒；`warm`对照中冷启动10.95秒→命中0.40秒。
   - 新增`seed --from lab-1`，把完整缓存复制到同型号GPU、同驱动的其他节点。
   - 试过`CUDA_MODULE_LOADING=EAGER`：超过10分钟仍未完成，缓存超过200 MB，已放弃。
2. **未下发片段改派**（B）：B阶段两次分别发生2次、1次改派，快节点不再空等慢节点手里的首片。缓存就绪后各节点同时就绪，改派次数为0，属于正常现象。
3. **协调循环耗时**（C、D）
   - 基线时每0.4秒一轮的tick实际要1～4秒，主要花在refresh/reconcile（串行K3s调用）和SQLite提交上：共享磁盘上synchronous=FULL时单次提交为5～115 ms，IO繁忙时达2.2秒。
   - 片段完成后到下一片派发之间常有1～3秒空档，单片实际处理只要0.4～0.7秒。
   - 改为两个循环：派发循环每0.15秒，维护循环每0.5秒。数据库仍以BEGIN IMMEDIATE复核状态，与原有的网关独立进程一致。
4. **控制面停顿容忍**
   - 一次运行中宿主磁盘出现严重争用：IO pressure full达14%，load最高87，大量进程处于D状态，K3s的kine也记录了1～2秒的慢SQL。数据库写入被阻塞10～37秒，心跳写不进去，结果四个健康会话全部被判心跳超时。该任务（`excluded-io-outage.json`）最终在600秒截止时超时失败，未计入统计。
   - 修复：协调器两步之间间隔超过8秒时，心跳超时判定暂缓一个窗口；容器自隔离租约从20秒改为60秒。结果仍由attempt令牌和active_attempt隔离。
   - 该次事故的Pod残留，原因是宿主IO导致containerd状态不一致（CRI violation）。确认进程已不存在后，手动force delete了这4个Pod对象。

## 部署状态

- 正式8310服务已运行这些改动。
- 四个lab节点均已存在`/var/lib/rancher/k3s/changan-cache/cuda`（UID 10001，0700，约91 MB）。
- `.env`中已设置`CHANGAN_CUDA_CACHE_HOSTPATH`。
- 驱动、ORT或GPU型号变化后，先运行`prepare_cuda_cache.py warm`，必要时再执行`seed`。

## 仍存在的限制与下一步

- 每片约0.5秒处理，但节点上的片间节奏约2.5秒（领取、下载、上传、回报都走HTTP加数据库）。下一步可让会话预取下一片，或增大GPU节点的分片。
- 控制面使用单个SQLite，放在共享机械盘或网络盘上，会受其他租户IO的影响。建议把`data/`放到本地SSD，并减少大事件的写入（no_candidate/decision事件携带完整的候选快照）。
- 冷缓存仍然存在“11秒或60秒”的不确定性。根治方法是使用含sm_120原生内核的ORT构建，或改用TensorRT EP并缓存engine。
