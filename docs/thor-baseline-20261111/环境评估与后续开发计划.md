## 1 评估结论

板卡具备进入项目单板适配的基础条件：真实 Thor GPU 可见，CUDA 设备内存操作通过，TensorRT 合成小算子已在 GPU 上正确执行，Docker 与 NVIDIA Container Toolkit 已安装。接下来应优先完成“真实板卡上的视频任务闭环”，沿用当前 K3s、任务内容器复用和真实事件展示路线。

目前还不能把它登记为已经可执行业务的节点。项目 YOLOX 模型、普通 GPU 容器、K3s Pod 和平台视频任务均未在此板验证。直接接入现有平台的主要障碍是双向网络、ARM64 制品，以及应用当前单镜像/单架构配置；无需重新设计任务、分片和结果协议。

官方当日下载说明将 Jetson Linux 39.2.1 对应到 JetPack 7.2.1。板上 L4T、CUDA Toolkit、cuDNN、TensorRT 版本与该配套相符；没有安装 `nvidia-jetpack` 元包，不能仅凭元包缺失认定 SDK 未装好。后续锁定实际组件版本，不沿用早期材料中的 JetPack 7.0 假设。来源与适用边界见《官方资料核对》。

本轮完成环境诊断和开发评估，未安装依赖、拉取镜像、配置网络、加入集群、重启服务或改动业务代码；未运行完整视频或性能基准。

## 3 已验证到哪一层

1. SSH 登录及 sudo 身份验证成功；密码未写入报告、证据或仓库。
2. CUDA Driver API 枚举到一张 Thor，计算能力 11.0；分配 4096 字节设备内存、写入固定值、回读逐字节一致，随后释放。
3. TensorRT 在内存中构建 FP32 的 `input + 1` 小网络，输入形状 1×16，GPU 执行输出 1—16，最大绝对误差为 0。整个诊断约 0.83 秒，包含建引擎等步骤；这不是 YOLOX 推理延迟，也不是业务性能指标。
4. `nvidia-container-cli info` 能枚举 GPU，但同时输出 NvRm/nvmap 权限相关告警，尽管退出码为 0。不能因此认定容器 GPU 已验证，也不据此判定驱动损坏；下一轮以普通非特权 GPU 容器实测查明是否影响执行。
5. 尚未验证：ARM64 项目镜像、YOLOX CPU/GPU 结果、K3s GPU Pod、B 模式会话、多板并行、取消重试、真实网络性能。

## 4 当前网络及接入障碍

板卡当前使用 Wi-Fi `wlP1p1s0`，地址 `192.168.50.151/24`，默认网关 `192.168.50.1`；有线网口未启用。另有 Jetson USB 网桥 `192.168.55.1/24`。本机到板卡 4 次 ping 无丢包，RTT 为约 7—212 ms；样本很小，不作为稳态网络指标。Wi-Fi 协商速率不是应用下载吞吐。

| 方向/端口 | 本轮结果 | 解释 |
|---|---|---|
| Mac → Thor TCP 22 | SSH 成功 | 当前管理入口可用 |
| Thor → 开发服务器 10.13.0.9:22031 | TCP 成功 | 仅证明该 SSH 入口可达，未在板卡保存开发服务器凭据 |
| 开发服务器 → Thor 192.168.50.151:22 | 3 秒内超时 | 当前没有证明双向可路由；不能视为对端 sshd 故障 |
| Thor → 10.13.0.9:6443、8311、5500 | 连接被拒绝 | 这些端口没有通过该地址向板卡提供可用服务 |
| Thor → github.com:443、nvcr.io:443 | TCP 成功 | 只证明连接建立，未验证认证、镜像拉取或下载速度 |

服务器当前网关绑定在 Docker 网桥 `172.29.1.1:8311`，业务回调地址也是该地址；镜像引用使用 `changan-registry:5000`。这些都是开发集群内部地址，不能直接交给实验室板卡。服务器 PID 1 为 sshd，属于既有嵌套开发环境；不应把该环境视为已经具备对外原生集群网络的管理主机。

**建议：**硬件验证单独使用真实 K3s 集群，板卡原生运行 agent；先与资源池基础设施负责人确定可稳定路由的控制面和 VPN/路由方案。优先使用已经具备条件的实验室管理节点或资源池提供的集群，开发服务器继续负责源码、构建和管理业务。若使用服务器侧控制面，需要先解决当前嵌套网络的可达性。未确认的额外管理硬件不能记作已到位。

网络验收至少包括：节点到 API Server 的 TCP 6443、所选 CNI 所需节点间流量（默认 VXLAN 为 UDP 8472）、管理侧的节点日志/状态通道，以及 Pod 到输入/回调网关与镜像仓库的实际访问。仅 SSH 登录或单端口转发不能证明多节点网络完整。仓库和回调应使用板卡及 Pod 可达的受控地址，校验 TLS 和访问凭据。

如网络调整耗时，可以用明确标识的临时隧道完成单板业务冒烟，但应记录拓扑和适用范围；它不能替代多节点 CNI 与正式链路验收。本轮未建立隧道或更改网络。

## 5 与当前代码架构的适配

已核对实际源码，而非仅依据旧交付说明。

| 位置 | 当前实现 | 下一步建议 |
|---|---|---|
| app/engine.py、app/container_execution.py | 创建任务时冻结 application；application 只有全局 CHANGAN_VIDEO_IMAGE 和 CHANGAN_IMAGE_ARCH | 增加应用制品的架构/运行时变体，并冻结任务可用变体；选定节点后解析实际镜像，历史任务仍用原快照 |
| app/container_execution.py:refresh、app/scheduler.py | 只有节点架构等于全局镜像架构才填入模型能力，否则会被模型兼容性过滤 | 按经过验证的应用变体判断节点能力；记录“不支持该架构/运行时”的具体原因 |
| app/session_execution.py | 一个任务在每个参与节点保留一个会话/模型，连续领取分片，任务后回收 | 保留 B 模式，在会话内固定架构、镜像摘要、模型摘要和实际后端 |
| app/kube.py | 单一 kubeconfig/cluster；Job 有目标节点与架构选择器、GPU 资源和 nvidia RuntimeClass | 单板先用隔离实例指向真实集群；统一多集群接入后续与资源池接口协同，不能只改 cluster_id 字符串 |
| deploy/Dockerfile.video-unified、相关锁文件和构建脚本 | 现有已验证制品为 amd64，Python 3.11，ORT 1.23.2，CUDA 12.8/cuDNN 9 依赖 | 新建经验证的 ARM64 制品，优先匹配板上 R39.2.1 配套；不要复制 x86 驱动或 wheel |
| workers/inference.py | Detector 直接依赖 ORT；支持 cpu/auto/cuda；GPU 依据 ORT 计算事件确认 | 首先验证可用的 ARM64 ORT CUDA 包；必要时抽出推理后端接口，增加 TensorRT 适配并保留相同预处理、后处理与结果契约 |
| CUDA 缓存与调度改派 | 已有节点缓存、未下发分片改派与准备时间记录 | 保留机制；缓存按硬件、驱动、运行时隔离；5090 seed 不能作为 Thor 缓存直接复用 |

同一应用可以有多份架构制品，业务仍是一套协议和一种通用 CPU/GPU 容器用法；无需增加“只能运行 GPU 的业务节点”，也不改成每片新建容器。

优先为单板配置隔离的 ARM64 应用实例完成闭环，避免立即修改正式四 lab 环境；要让同一个任务跨 amd64 和 arm64 执行，再完成上述变体解析。OCI 多架构索引也可作为交付形式，但仍需记录实际平台镜像摘要和运行时兼容条件，不能只换标签。

**推理运行时决策门：**先用半天左右验证 ARM64 ORT CUDA 包的版本、来源、sm_110 支持和真实 YOLOX GPU 执行；可用则复用 Detector。若没有可复现的兼容包，转用已经通过基础运算的 TensorRT 10.16 路线，先验证相同 ONNX 的解析与 FP32 输出，再接入后端接口。不能预设“pip 安装成功”等同于 CUDA 已执行，也不能因为宿主 CUDA 是 13 就断言所有携带 CUDA 12 用户态库的容器必然无法运行。

TensorRT engine 按模型摘要、TensorRT/CUDA 版本、GPU 架构、精度和输入形状建立缓存。先 FP32 正确性，再决定 FP16；不将 TensorRT、小模型替换或量化同时混入首轮闭环。CPU 路径保留于同一业务镜像，auto 回退必须显示原因，严格 GPU 验证不允许以 CPU 回退算通过。

Thor 的 CPU/GPU 使用共享物理内存。本轮 nvidia-smi 总显存字段为 Not Supported，CUDA 可分配量与系统可用量是不同观测口径；资源池不得把两者相加成两份独立容量。先一个执行槽，按模型峰值内存实测决定容器预算；现有 2 GiB 只是服务器起点，不能当作 Thor 已验证上限。
