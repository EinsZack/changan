# 容器启动、多节点差异、GPU环境与架构评估（2026年11月10日）

本轮基于GitHub main `084882f`（0.5.2）源码、Codex同日两份排查证据（`docs/gpu-init-diagnostic-20261110/`、`docs/session-participation-20261110/`）及公开资料完成代码审阅，并实现两项修改。**修改仅完成单元/回归测试，尚未在服务器部署和正式任务验证**；下文凡称“预期”的效果均待服务器实测确认。四lab为同一服务器的逻辑节点，不能作为THOR实机结论。

## 结论速览

| 问题 | 结论 | 本轮处理 |
|---|---|---|
| 1 启动慢 | 主因是GPU首次前向的PTX即时编译（55～78秒）。ORT 1.23.2的CUDA 12轮子缺少RTX 5090（sm_120）原生代码，驱动需现场编译。业务容器以UID 10001运行，HOME=/且根文件系统只读，编译缓存无法写入，所以每个新Pod都要重新编译。容器创建、镜像和Python导入合计仅约4～6秒 | 已实现节点本地持久CUDA缓存及预热脚本 |
| 2 四容器差异大 | 不是K8s层排队：四个Pod在约1.6秒内全部创建，在约9～11秒内全部认领，并在同一秒开始预热。差异全部发生在首次CUDA前向内部。此外，首片在创建会话时就绑定给慢容器，快容器做完其余片段后只能空等（约24秒尾部） | 已实现未下发片段改派；缓存命中后预热差异预计随之消失 |
| 3 镜像环境 | 对ORT CUDA EP而言完整（cudart/cuBLAS/cuDNN/cuFFT/cuRAND/NVRTC），驱动由nvidia runtime注入，四lab已实测真实CUDA。缺可写JIT缓存（已补），缺TensorRT（最大的性能杠杆），仅amd64，解码和前后处理仍在CPU | 记录为后续项 |
| 4 架构 | 状态机、执行权隔离、幂等和证据链设计扎实，保留。不足在于：调度推式绑定，代价模型不含启动成本，数据面经控制面中转，每2秒轮询K8s，以及单一镜像摘要无法同时覆盖x86与ARM | 改派已实现；其余见路线图 |

## 1 启动耗时构成

以task_780767757a54421c为例（相对任务started）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 视频切分 | 约3.8～5.4秒 | 会话创建前的prepare |
| 会话创建→Pod认领 | 约4～5秒 | Secret/Job创建、调度、容器启动（镜像已缓存）、导入cv2/ORT/numpy |
| 设备探测+ORT会话创建 | 0.3～1.2秒 | |
| **首次CUDA前向** | **11～57秒** | PTX JIT；CPU模式仅0.05秒 |

根因链：
1. RTX 5090的计算能力为sm_120。官方onnxruntime-gpu 1.23 CUDA 12轮子未包含部分算子的sm_120 SASS，只能由驱动把PTX JIT成本机代码。`CUDA_DISABLE_PTX_JIT=1`时报`cudaErrorJitCompilationDisabled`，可佐证这一点（见gpu-init-diagnostic）。
2. JIT结果本应写入`~/.nv/ComputeCache`，但Pod的HOME=/、根文件系统只读、用户为10001，写入失败，每个新进程都会重新编译。
3. B模式每个任务新建Pod、任务结束回收，所以每个任务都要付这笔代价。同一Pod内的后续分片不受影响。

已排除：模型读取（20 MB，0.2秒）、镜像拉取（IfNotPresent且已缓存）、profile开关（缓存命中时开着profile也只需0.93秒）、容器cgroup CPU节流（nr_throttled未增加）。

## 2 四容器启动差异与“排队”

- **K8s/调度层没有排队**：四个会话分别在+3.8/+4.3/+4.8/+5.4秒创建，+9.0～+10.7秒全部认领，四个warmup在同一秒内开始。
- **差异全部发生在JIT内部**：单节点单独运行时为55～58秒；四节点并发时，有的只需约11秒，有的约57秒，呈“双峰”分布。由此可见并非“同时启动、互相拖慢”：并发时部分容器反而比单独运行更快。现有证据未保存每个进程的JIT profile，**无法确定双峰的具体原因**。可以确认的是，JIT为CPU密集型（单进程约占1核持续60～77秒）；lab节点仅用`docker --cpus 3`限额而未绑核，与服务器上其他应用共享物理CPU，这类争用会放大波动。
- **真正类似“排队”的现象在业务调度层**：`submit()`创建会话时，就把首片写入该会话的active_attempt（WAITING_SESSION）。engine只分配PENDING片段，快容器无法接手这个片段，只能等慢容器就绪。三次任务的片数分布为1/8/7/8、2/1/20/1、10/1/12/1，就是这个机制造成的。

## 3 本轮代码修改

### 3.1 节点本地持久CUDA编译缓存

- `app/kube.py`：GPU会话Pod新增`cuda-cache`卷，挂载到`/cache/cuda`，并设置`CUDA_CACHE_PATH`和`CUDA_CACHE_MAXSIZE`（默认1 GiB，上限4 GiB）。
  - 配置了`CHANGAN_CUDA_CACHE_HOSTPATH`时，使用节点hostPath（type=Directory，目录须预先存在），跨Pod、跨任务复用。
  - 未配置时退回Pod级emptyDir，仅在Pod存活期间有效。
  - 只读根文件系统、非root等安全设置不变；CPU会话的Pod不变。
- `app/container_execution.py`：新增`cuda_cache_settings()`，在任务创建时冻结进application，旧任务不受影响。
- `scripts/prepare_cuda_cache.py`：
  - `prepare`：在四个lab节点容器内创建UID 10001所有、权限0700的目录。默认路径`/var/lib/rancher/k3s/changan-cache/cuda`位于k3d节点的Docker卷上，节点升级或重建时保留。
  - `warm`：空闲时依次在每个节点运行一次同镜像的预热Job，输出首次前向耗时和缓存大小。
  - `status`：查看各节点的缓存文件数和字节数。
- 并发安全：CUDA驱动本身支持多进程共享同一缓存目录；驱动版本变化时会自行使旧条目失效。

预期效果（待验证）：Codex此前做过同Pod、跨新进程的测试，缓存命中后首次前向为0.69～0.93秒。跨Pod的hostPath复用是本轮新增，必须在服务器上用两个独立任务对照确认。

### 3.2 未下发片段改派给已就绪容器

- `SessionExecution.rebalance(task_id)`，由`engine.tick`在读取PENDING片段前调用（仅限task_session模式）。
- 触发条件：本任务存在READY且空闲的会话，且这些会话的数量多于现有PENDING片段。
- 只改派同时满足以下条件的尝试：处于WAITING_SESSION、`execution_id`为空（容器从未拿到）、所属会话为STARTING且未ready。
- 在一个`BEGIN IMMEDIATE`事务内复核上述条件，然后：
  - 尝试置为CANCELED；
  - 片段回到PENDING，**不计重试次数**；
  - 会话的active_attempt清空，会话本身保留，就绪后可继续承接剩余片段；
  - 写入`segment_reassigned`事件（含来源节点、已等待秒数、`retry_counted: false`）。
- 与`/next`的竞争：`/next`同样在写事务中只把`ready_at`非空会话的active_attempt交给容器。两者在SQLite中串行执行，因此不会出现慢容器迟到后又领到同一片段的情况。测试已覆盖“改派后慢容器就绪调用/next只得到wait”。
- 没有采用以下做法：强行平均片数、让所有节点等最慢的容器、恢复逐片建Pod。

### 3.3 测试

新增`tests/test_session_rebalance.py`共6项：改派、已下发不改、已就绪不改、PENDING已足够时不改、GPU Pod缓存挂载和环境变量、配置校验。全量123项通过。另有2项失败，原因是仓库不含模型和示例视频（`assets/models`、`assets/samples`被gitignore），修改前后一致，在服务器上应会通过。前端未改动（新事件按原样在事件列表中显示）。

## 4 镜像与GPU调用评估

| 项 | 现状 | 评价 |
|---|---|---|
| 基础镜像 | python:3.11-slim，加上pip安装的nvidia-*-cu12运行库 | 比CUDA官方基础镜像小，对ORT CUDA EP而言完整 |
| 驱动注入 | runtimeClass nvidia，每个lab一个device plugin，NVIDIA_VISIBLE_DEVICES指向同一张5090 | 四Pod时分共享，无显存隔离，仅靠ORT `gpu_mem_limit=1GiB`自律；作为开发模拟可以接受 |
| CPU/GPU切换 | `CHANGAN_MODEL_DEVICE=auto`时先试CUDA，失败则显式回退并记录原因 | 合理，便于以后接入不同板卡 |
| JIT缓存 | 原先缺失 | 已补 |
| TensorRT | 无 | YOLOX这类CNN用TensorRT FP16通常还能明显提速；THOR上也应走这条路线 |
| 解码/前后处理 | cv2 CPU，逐帧同步`session.run` | GPU前向5 ms/帧后，CPU解码和前后处理会成为主要耗时 |
| 架构 | 仅amd64，`CHANGAN_VIDEO_IMAGE`为单一摘要 | 接入THOR需要按架构区分镜像 |

## 5 架构评估

值得保留：
- 持久状态机（任务/片段/尝试/会话），配合令牌和Pod UID双重隔离执行权；
- 迟到结果拒收，结果来源和产物摘要校验；
- B模式下每个任务、每个节点一个会话，模型只加载一次；
- 镜像摘要固定，安全上下文严格；
- 计时证据完整，并注意区分模拟与实测。

需改进（按优先级）：
1. **推式绑定 → 拉式工作队列**（本轮先做了有界改派）。长期建议：调度器只决定“哪些节点加入本任务”，片段由就绪会话从任务队列中按序领取（work-stealing）。异构节点（GPU与CPU，THOR与MT8676）吞吐相差10倍以上时，这种方式天然负载均衡，也更符合车群节点随时加入或退出的场景。
2. **代价模型不含启动成本**：`scheduler.choose`只计算、传输和排队三项。建议加入“会话预计就绪时间”（冷启动/热缓存、是否已有会话），并按CPU/GPU后端分别记录measured_fps。
3. **分片粒度**：1秒片在GPU上约0.5秒处理完，HTTP下载/上传/回报和0.25～0.4秒的轮询间隔占比很高。GPU节点宜用更大的片，或按节点吞吐动态切片。
4. **数据面经控制面中转**：片段由平台HTTP下发、预览图回传。实车场景下视频产生在车端，宜让数据就近处理，平台只做编排。
5. **控制面轮询**：每2秒对每个会话做job/pods/events的list，节点或任务一多就会给API server带来压力。建议改用watch/informer。
6. **单SQLite、单协调循环**：现阶段规模下没有问题。车群规模扩大后，需要考虑多协调者和租约（与“I2租约服务端”待开发项一致）。

## 6 THOR到位后的方案

> 以下为方案建议；THOR实机尚未到位，版本号来自公开资料，到货后以板端实际JetPack版本为准。

- 平台：Jetson AGX Thor为Blackwell GPU，计算能力sm_110，搭载JetPack 7（Ubuntu 24.04、CUDA 13、cuDNN 9、TensorRT 10），采用SBSA架构，可使用标准NVIDIA Container Toolkit。每块板以k3s agent（arm64）加入集群，由containerd通过nvidia runtime调用GPU，沿用当前的runtimeClass和device plugin模式。
- 镜像：PyPI上没有aarch64+CUDA 13的onnxruntime-gpu。可选方案：
  - (a) 以NVIDIA L4T/TensorRT容器为基础，**直接使用TensorRT**（推荐）；
  - (b) 自行编译ORT（`CMAKE_CUDA_ARCHITECTURES=110`），启用TensorRT EP。
  - 平台侧需把单一`CHANGAN_VIDEO_IMAGE`改为按架构区分的镜像（manifest list或`{arch: digest}`映射）。调度器已有architecture过滤，可以复用。
- **启动成本会以另一种形式重现**：TensorRT首次构建engine可能需要数十秒到数分钟。必须沿用本轮的“节点本地持久缓存+入网预热”模式，持久化engine/timing cache（以TensorRT版本、模型sha、GPU型号为键），或预先构建后随模型分发。本轮的`prepare_cuda_cache.py`和hostPath挂载可以直接推广为“节点运行时缓存”。
- 解码：GPU推理变快后，ARM CPU解码会成为瓶颈，宜使用NVDEC（GStreamer/DeepStream或PyNvVideoCodec）。
- 内存：THOR的CPU和GPU共用统一内存。现在K8s内存request与ORT `gpu_mem_limit`分开设置，在THOR上应合并核算。
- 镜像分发：CUDA/TensorRT镜像体积在GB级，车端网络不稳定，应在节点入网时预拉取，配合边缘镜像仓库和固定摘要（已具备）。
- 与MT8676的关系：保留`model_policy`抽象，后续可扩展为`cpu/cuda/tensorrt/neuron`，由节点能力标签驱动选择。

## 8 服务器部署与验证步骤

```bash
cd /root/projects/changan-orchestrator && git pull --ff-only origin main
conda activate changan-orchestrator && pytest -q          # 期望全部通过
python scripts/prepare_cuda_cache.py prepare              # 四lab创建10001可写目录
echo 'CHANGAN_CUDA_CACHE_HOSTPATH=/var/lib/rancher/k3s/changan-cache/cuda' >> .env
python scripts/manage.py restart                          # API与容器网关都需重启
python scripts/prepare_cuda_cache.py warm                 # 第一次约1分钟/节点，填充缓存
python scripts/prepare_cuda_cache.py warm --node lab-1    # 再跑一次，应降至约1秒
python scripts/prepare_cuda_cache.py status
```

验证项：
1. 提交两个1秒、15fps的正式任务，确认它们使用不同的Pod，每个Pod只加载一次模型，`warmup_seconds`从数十秒降到约1秒，检测结果与之前一致。
2. 人为让某节点变慢（例如对其缓存目录执行`chmod 000`），确认出现`segment_reassigned`事件、24片240帧完整、`retries`为0，并且慢节点就绪后仍会参与处理。
3. 取消或重启场景下，旧执行仍然被隔离。
