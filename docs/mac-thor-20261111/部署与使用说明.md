## 启动、停止与重启

Redis、Zot和防空闲睡眠服务由用户LaunchAgent管理：`local.changan.redis`、`local.changan.registry`、`local.changan.awake`。

本机实测launchd启动的Python无法访问Thor，报Errno65，而相同解释器从当前用户会话启动访问正常。因此API和网关由用户会话启动为后台进程；旧API/网关LaunchAgent已停用并归档。没有更改系统隐私或防火墙设置。

**Mac重启后，登录用户会话并执行下列命令启动平台：**

```bash
source /opt/homebrew/Caskroom/miniforge/base/etc/profile.d/conda.sh
conda activate changan-platform
python "/Users/eins/Library/Application Support/ChanganPlatform/current/scripts/install_native_services.py" \
  --root "/Users/eins/Library/Application Support/ChanganPlatform" \
  --env-prefix "/opt/homebrew/Caskroom/miniforge/base/envs/changan-platform" \
  --gateway-host 192.168.50.231
```

脚本复用已运行的服务，并通过PID及进程创建时间避免重复启动。API/网关后台运行，不需要保留终端窗口；它们目前没有launchd故障自动拉起能力。查看状态或停止平台：

```bash
cd "/Users/eins/Library/Application Support/ChanganPlatform/current"
python scripts/manage.py status
python scripts/manage.py stop api container-gateway
```

仅重启API/网关时，在没有活动任务的情况下：

```bash
CHANGAN_SKIP_REDIS=1 python scripts/manage.py restart api container-gateway
```

使用期间保持Mac开机、联网、用户会话可用。caffeinate防止空闲睡眠，不保证合盖仍在线。当前IP尚未设置路由器固定租约；地址变化后需同步网关配置、仓库地址/证书和Thor信任配置。

## Thor镜像和GPU配置

构建入口为服务器`scripts/build_thor_runtime.py`。基础镜像固定到Linux ARM64的Python3.12-slim-trixie摘要；ORT采用Jetson AI Lab提供、实际包含sm_110代码的1.24.0 wheel，配套CUDA13.2及cuDNN9.20依赖，模型为既有YOLOX Tiny。CUDA 13 wheel实际安装在`nvidia/cu13/lib`，镜像已设置该目录与cuDNN目录的`LD_LIBRARY_PATH`，解决ORT旧预加载器查找路径不兼容。所有wheel均按SHA256锁定；QEMU只用于服务器依赖构建阶段，最终镜像不含QEMU，也不在Mac构建。

初版通用PyPI ORT1.31.1已实测可做CPU视频流程，但CUDA运行报`cudaErrorNoKernelImageForDevice`，不能作为Thor GPU成功制品。新版以普通Pod与完整视频任务的实际CUDA证据验收。

服务器导出OCI归档后传到Mac，用专用环境执行`scripts/publish_oci_archive.py`并校验项目CA即可上传，无需Mac容器引擎。Zot使用2.1.23 minimal原生ARM64二进制；大镜像传输读写超时已设10分钟。发布配置使用不可变摘要，不依赖可覆盖tag。

Thor采用K3s v1.35.5+k3s1、NVIDIA RuntimeClass及设备插件v0.20.1。插件必须设置`DEVICE_ID_STRATEGY=index`，该板默认tegra设备ID与现有Toolkit不兼容。

业务容器维持UID10001、只读根目录、禁提权和drop ALL。实测设备访问需要video(44)/render(993)，设置`CHANGAN_GPU_SUPPLEMENTAL_GROUPS=44,993`，仅加入GPU工作负载，并冻结到任务应用快照；没有放宽宿主设备权限。CUDA缓存使用节点目录`/var/lib/rancher/k3s/changan-cache/cuda`，由UID/GID10001持有。

仍为B模式：每任务/参与节点一个容器，模型加载一次，连续处理多个分片，结束后回收；不存在跨任务常驻模型服务。

## 数据迁移及复跑

已迁移原104条历史任务、数据库和引用文件，逐一验证1,319个分片文件；各表逐行一致，仅`segments.path`重定位为Mac路径。SQLite完整性、外键检查通过，迁移前副本与报告保存在`data/backups`及`data/migration-verification.json`。

真实视频复跑脚本随发布制品提供：

```bash
python "/Users/eins/Library/Application Support/ChanganPlatform/current/scripts/validate_thor_native.py" \
  --root "/Users/eins/Library/Application Support/ChanganPlatform" \
  --node thor1 --expect-backend cuda
```

脚本上传24秒演示视频，切为6片、采样240帧，检查真实thor1落点、单会话/一次模型加载、CUDA计算事件、预览读取和全部容器清理；证据保存至`data/evidence/thor-native-20261111`。运行前确认没有其他在途任务。

最终镜像摘要、视频任务ID及本轮验收结果见同目录《交付说明》和《版本核对》。本轮只验证单板功能，不据此推导四板吞吐、端到端加速或车载网络可靠性。

## 后续开发顺序

先冻结单Thor制品；用户启用其余三板后逐板核查JetPack、设备组和网络，加入Thor1集群并分别执行真实任务。随后验证四板分片调度、取消/重试、断连与恢复，完善按物理设备区分的展示和分段计时，再与资源池同学的正式采集注册接口联调。多板指标、GPU视频解码、TensorRT/FP16和稳定性能对照仍待后续实测。
